# V1.5 — SECURITY CENTER REPORT

## 1. Auditoria

Antes de implementar, li: `system_monitor/` (service.py, models.py, processes.py,
network.py, gpu.py), `security/` (audit.py, confirmations.py, permissions.py — V1),
`tools/` (base.py, applications.py, filesystem.py, system.py), `core/events.py`,
`core/lifecycle.py`, `core/tool_manager.py`, `main.py`, `settings/config.py`,
`ui/desktop/dashboard/` inteiro, `memory/database.py`, `memory/service.py`.

Conclusões da auditoria (antes de qualquer código novo):

1. **`SystemMonitorService` já coleta processos** (`ProcessSnapshot` via
   `PROCESS_LIST_UPDATED`) — reaproveitável diretamente, sem segunda enumeração.
2. **`SystemMonitorService` não coletava conexões de rede por processo** — só
   agregados de bytes/s totais (`NetworkMetrics`). Dado genuinamente novo e necessário,
   justificando `security/network_analysis.py`.
3. **`security/` (V1) já tinha `PermissionManager`, `ConfirmationService`,
   `AuditLogger`** — nenhum precisou ser reescrito; o Security Center só passou a
   *usar* `AuditLogger` (ver seção 16), sem alterar sua implementação.
4. **`EventBus` (`core/events.py`) já era o barramento único** de todo o Steve —
   reaproveitado integralmente, nenhum segundo barramento criado.
5. **`ui/desktop/dashboard/window.py`** já tinha um padrão claro e replicável para uma
   nova aba (view "burra", `DashboardWindow` dona de todas as assinaturas do
   EventBus) — seguido à risca para a aba Security.
6. **`tools/base.py::Tool`** já suportava ferramentas com dependências injetadas no
   construtor (`RememberFactTool(memory_service=...)`) — mesmo padrão usado para as
   novas ferramentas de segurança.

## 2. Arquitetura

`security/` ganhou: `models.py`, `events.py`, `risk.py`, `rules.py`,
`authenticode.py`, `file_analysis.py`, `network_analysis.py`, `process_analysis.py`,
`scanner.py`, `engine.py` — cada um com responsabilidade única (ver
`docs/ARCHITECTURE.md`'s seção V1.5 para o detalhamento completo de cada módulo).
`security/audit.py`, `security/confirmations.py`, `security/permissions.py` (V1)
permanecem intocados. `ui/desktop/dashboard/security_tab.py` é a quinta aba da
`DashboardWindow` existente — nunca uma segunda janela/aplicação.

## 3. Security Engine

`security/engine.py::SecurityEngine` é o núcleo. Ciclo de vida espelha deliberadamente
o modelo endurecido do PATCH 03 (`_lifecycle_lock`, thread daemon nomeada
`steve-security-engine`, `_stop_event`, `thread.join()` com timeout e log se excedido).

**Diferença deliberada do System Monitor**: inicia dentro de
`main.build_app_services()` (no boot), não quando o Dashboard abre — "proteção em
tempo real" que só funciona com o Dashboard aberto não seria tempo real. Para de
funcionar apenas no shutdown completo do Steve.

## 4. Process Monitor integration

`security/process_analysis.py::ProcessAnalyzer` consome o `ProcessSnapshot` do
`SystemMonitorService` via assinatura em `PROCESS_LIST_UPDATED` — nenhuma segunda
chamada a `psutil.process_iter()`. Primeiro ciclo estabelece uma baseline silenciosa
(nada já em execução é "novo"); só processos que aparecem depois são avaliados.
Metadados de arquivo são cacheados por caminho (nunca re-hasheados a cada ciclo).

## 5. File Analysis

`security/file_analysis.py` — `pathlib.Path.stat()` + leitura em stream para hash.
**Nunca executa, abre para interpretar conteúdo, ou carrega como código** o arquivo.
Verificado com um teste dedicado que confirma que o conteúdo/mtime do arquivo
analisado nunca muda. Arquivos acima de 200MB não são hasheados nesta versão
(`UNKNOWN`, não um hash de leitura truncada, não um erro).

## 6. Hash Analysis

SHA-256 via `hashlib`, leitura em chunks de 1MB (memória constante, independente do
tamanho do arquivo). Verificado com valores reais conhecidos (hash de
`C:\Windows\System32\notepad.exe` calculado e conferido). O hash é o identificador da
amostra — nenhuma consulta de reputação automática existe nesta versão (ver seção 27).

## 7. Network Analysis

`security/network_analysis.py` — `psutil.net_connections(kind="inet")` (a mesma
informação do `netstat -ano`), filtrado a conexões com endereço remoto real
(excluindo loopback e sockets em LISTEN). Nunca conteúdo de pacote, nunca MITM, nunca
TLS. Sobrevive a `AccessDenied`/processo já encerrado sem lançar exceção (testado).

## 8. Risk Engine

`security/risk.py::assess()` — uma `Severity` sempre vem com os sinais concretos que a
produziram (`RiskAssessment.signals`), nunca um número sem explicação. **Um único
sinal fraco nunca produz HIGH/CRITICAL sozinho** — regra explícita, testada
diretamente (inclusive com um sinal de peso artificialmente alto, para provar que o
limite é uma garantia rígida, não uma propriedade emergente dos pesos escolhidos).

## 9. Rules

`security/rules.py` — sinais nomeados e testáveis isoladamente: localização incomum
(temp/downloads), extensão dupla disfarçada (`invoice.pdf.exe`), processo novo,
ausência de assinatura digital confirmada, arquivo criado recentemente, conexão
externa. Heurísticas estruturais simples — **não** um motor de assinaturas de
antivírus.

## 10. Findings

`SecurityFinding` (`security/models.py`) — dataclass congelada com id, timestamp,
severidade, categoria, título, descrição, evidências (tupla de motivos concretos),
confiança, processo/PID/caminho quando aplicável, e status (DETECTED/REVIEWED/
DISMISSED — nunca um "THREAT_CONFIRMED"). A única mutação possível é o status,
via `SecurityEngine.update_finding_status()` (`dataclasses.replace`, nunca alterando
severidade/evidência).

## 11. Scan Engine

`security/scanner.py::SecurityScanner` — Quick Scan (executáveis dos processos em
execução, deduplicados por caminho), Scan File, Scan Folder (limitado a 500 arquivos
por scan, cancelável durante a própria enumeração da pasta). Protegido por um lock
(no máximo um scan por vez, testado deterministicamente com sincronização real via
`threading.Event`, não uma corrida de sorte). Cancelamento testado com
`threading.Event`s reais provando que o scan para genuinamente no meio do trabalho
(menos arquivos escaneados que o total disponível).

## 12. Dashboard

`ui/desktop/dashboard/security_tab.py::SecurityTab` — quinta aba da `DashboardWindow`
existente. Mostra estado de proteção (colorido: verde=PROTEGIDO, azul=MONITORANDO,
amarelo=DEGRADADO, cinza=DESATIVADO), achados recentes numa tabela (severidade/título/
categoria/status) com painel de detalhes (evidências completas ao selecionar), e três
botões de scan com barra de progresso e cancelamento. Nenhuma ação de mover/apagar/
executar existe em nenhum botão.

## 13. EventBus

8 eventos novos (`security/events.py`): `SECURITY_ENGINE_STARTED/STOPPED/ERROR`,
`SECURITY_FINDING_CREATED`, `SECURITY_SCAN_STARTED/PROGRESS/COMPLETED/CANCELLED` — todos
no `EventBus` já existente e compartilhado. "Steve Core" (Live Activity) ganhou linhas
estilizadas para eles também. Nenhum segundo EventBus foi criado.

## 14. AI integration

`tools/security.py` registra `check_security_status`, `list_security_findings`
(somente leitura) e `scan_file` (lê e hasheia um arquivo a pedido explícito, nunca o
executa). Fluxo sempre: evidência real → `SecurityEngine` → `SecurityFinding` → IA
contextualiza via tool-calling nativo já existente. Nenhuma ferramenta permite à IA
criar, aprovar ou descartar um achado — verificado estruturalmente (teste confirma que
`ListSecurityFindingsTool` não tem nenhum método `create_finding`/`add_finding`).

## 15. Permissions

Todas as três ferramentas novas são `PermissionLevel.LOW` (mesmo nível de
`OpenFileTool`/`CheckCPUTool` — leitura/análise, não uma ação sensível pelo modelo de
permissões já existente). Nenhuma ação de maior impacto (mover, apagar, bloquear) foi
implementada nesta versão — logo, nenhuma nova integração com `PermissionManager` além
do nível LOW já existente foi necessária.

## 16. Audit Log

**Adicionado nesta revisão do relatório** (gap encontrado ao revisar a seção 29 do
spec): `SecurityEngine` agora aceita um `AuditLogger` opcional (mesmo padrão de
`LifecycleManager`'s `event_bus` opcional) e registra: scan iniciado, scan concluído
(com contagem de arquivos/achados), achado criado (id/severidade/categoria/título/pid/
nome do processo — nunca conteúdo de arquivo), achado revisado/dispensado, e erros de
análise. Testado que nenhum desses registros nunca inclui conteúdo de arquivo,
senha, token ou secret (a redação já existente de `AuditLogger._redact()` cobre isso
estruturalmente).

## 17. Privacy

Tudo local. Nenhuma chamada de rede é feita pelo Security Center em si (verificado
estruturalmente: nenhum `requests`/`urllib`/`http.client`/`socket.socket` em nenhum
módulo de `security/`) — a única atividade de rede observada é leitura passiva de
metadados de conexões já existentes via `psutil` (nunca abrir uma conexão nova).
Nenhuma telemetria.

## 18. Performance

Medido ao vivo, através da wiring de produção completa
(`main.build_app_services` → `SteveApp`), nesta máquina de desenvolvimento (AMD Ryzen
16 lógicos/10 físicos, AMD RX 6750 XT + Intel UHD 770):

| Métrica | Valor medido |
|---|---|
| Boot completo (inclui Security Engine iniciando) | ~2.1s |
| Abertura do Dashboard (5 abas, inclui Security) | ~75-100 ms |
| Quick Scan (35-90 executáveis, cache frio/quente) | ~70-525 ms |
| Shutdown normal | ~1-5 ms |
| Shutdown com hash grande em andamento (achado real) | até ~5.3s (dentro do orçamento de 10s do `THREAD_JOIN_TIMEOUT_SECONDS`) |
| CPU do processo Steve (ocioso, após boot) | 0-23% (variação normal, já registrada em etapas anteriores) |
| RSS do processo Steve | ~78 MB |
| Threads do processo | ~26 |
| Ciclo isolado create→start→stop do SystemMonitorService (sem carga concorrente) | ~450-500 ms |

**Cache/otimizações aplicadas**: metadados de arquivo (`ProcessAnalyzer._file_cache`)
nunca são recomputados para o mesmo caminho; a espera entre ciclos de análise
(`_new_data_event`) é interrompida assim que dados novos chegam, evitando ficar parado
um intervalo inteiro desnecessariamente (ver seção 4 do relatório de achados, PATCH 04
já havia estabelecido o mesmo princípio para nomes de adaptador de GPU/VRAM total).

## 26. Limitações

- **Verificação de assinatura Authenticode**: tentada via `ctypes`+`WinVerifyTrust`,
  testada contra binários reais conhecidos (`notepad.exe`/`cmd.exe`, assinados pela
  Microsoft) — o resultado foi o oposto do correto em ambas as direções. Revertida
  para sempre retornar "não verificado" (`None`) nesta versão, por decisão explícita
  de nunca apresentar uma fonte comprovadamente não confiável como verdadeira. Ver
  `security/authenticode.py` e `docs/ARCHITECTURE.md`.
- Heurísticas estruturais (localização, extensão, idade, assinatura, conexão), não um
  motor de assinaturas de malware — "SAFE" nunca significa "garantidamente livre de
  malware".
- `scan_folder_path` limitado a 500 arquivos por scan nesta versão.
- Arquivos acima de 200MB não são hasheados (classificados `UNKNOWN`).
- **Instabilidade de timing sob carga extrema de teste** (achado real durante a
  verificação desta etapa, não hipotético): rodar a suíte completa de 501 testes
  JUNTO com uma segunda execução pesada simultânea (uma condição que eu mesmo criei ao
  verificar múltiplas vezes em paralelo, nunca um cenário real de uso do Steve) expôs
  que o ciclo real de coleta do `SystemMonitorService` pode ocasionalmente parar por
  bem mais que os 10s de `THREAD_JOIN_TIMEOUT_SECONDS` sob contenção severa de
  recursos do sistema. Isolado (sem uma segunda execução pesada concorrente), 40
  ciclos completos de create/start/stop levaram consistentemente ~450-500ms cada — a
  causa é contenção de recursos do ambiente de teste sob carga artificial, não um
  defeito de lógica. Os testes do Security Engine que dependiam dessa temporização
  real foram desacoplados (usam eventos publicados manualmente em vez de esperar uma
  coleta real), tornando-os determinísticos independente da carga do sistema.

## 27. Riscos

- Se o mecanismo de assinatura digital for revisitado no futuro, deve ser testado com
  o mesmo rigor empírico usado aqui (binários conhecidos assinados E não assinados)
  antes de voltar a alimentar `unsigned_signal`.
- A soma de sinais em `risk.py` usa pesos fixos, escolhidos por julgamento, não
  calibrados estatisticamente contra uma base real de amostras maliciosas/benignas —
  aceitável para uma primeira versão baseada em heurísticas explícitas, mas os pesos
  podem precisar de ajuste com uso real.
- Nenhuma consulta de reputação (hash → conhecido-malicioso) existe ainda — um
  arquivo com hash de malware conhecido não seria sinalizado só por isso nesta
  versão (ver seção 28).

## 28. O que NÃO foi implementado

Conforme instruído explicitamente: Security Intelligence via web, consulta automática
de reputação, quarentena automática (nem preparação arquitetural além do que os
estados FileScanResult já expressam), exclusão/movimentação/bloqueio automático de
arquivo, encerramento/suspensão automático de processo, desabilitar Defender/Firewall/
UAC, execução de qualquer código baixado, autoatualização, autoaperfeiçoamento do
próprio Security Engine, comandos de voz destrutivos, interceptação de conteúdo de
rede/MITM/TLS, telemetria. `core/orchestrator.py`, `ai/router.py`, `memory/`,
`voice/`, `ui/desktop/orb/`, `core/lifecycle.py`, o modelo de tool-calling nativo, e o
lifecycle do `SystemMonitorService` corrigido no PATCH 03 não foram alterados (exceto
o aumento do limite de captura de processos em `ProcessCollector.sample()`, justificado
na seção 26 — necessário para que o Security Center visse processos ociosos, sem
afetar a aba Processes do Dashboard, que já tinha seu próprio limite de exibição
independente).
