# Relatório Técnico — STEVE V1.4: System Dashboard

## 1. Resultado da auditoria

Antes de qualquer alteração, li `core/events.py`, `core/lifecycle.py`,
`core/orchestrator.py`, `core/session.py`, `core/context.py`, `tools/system.py`,
`tools/applications.py`, `tools/filesystem.py`, `ui/desktop/` (window, app, controller,
async_bridge, status_bar, styles), `main.py`, `settings/config.py`, `security/audit.py`
e `tests/`. Conclusões:

1. **Métricas já reutilizáveis**: `tools/system.py` já usava `psutil` para CPU/RAM/disco
   (`CheckCPUTool`/`CheckRAMTool`/`CheckDiskTool`); `tools/applications.py` já usava
   `psutil.process_iter` para listar processos. `system_monitor/` reaproveita a MESMA
   biblioteca em vez de introduzir uma segunda forma de coletar os mesmos dados —
   nenhuma dessas ferramentas foi alterada, e nenhuma passou a chamar `system_monitor/`
   nesta etapa (permanecem independentes, ambas simplesmente usam `psutil`).
2. **`core/events.py::EventBus`** já existia (V1.3) mas só era usado por
   `core/lifecycle.py` até esta etapa — exatamente o mecanismo pedido para o Dashboard,
   sem precisar criar nada novo.
3. **Sem mecanismo de atualização periódica genérico** — só existia
   `ui/desktop/async_bridge.py::BackgroundRunner` (fila + `widget.after()`, para tarefas
   de UMA execução, não um coletor contínuo). `SystemMonitorService` precisou de sua
   própria thread de longa duração; reaproveitou o `BackgroundRunner` **já existente da
   janela principal** só para a marshalling final (evento → widget), não como coletor.
4. **Como a GUI recebe atualizações assíncronas**: `BackgroundRunner.post(callback,
   *args)` enfileira e `widget.after(40ms, drain)` drena na thread principal — usado
   desde a V1.1.5 para respostas do Orchestrator/voz. Reaproveitado sem mudança.
5. **Onde colocar o System Monitor**: `system_monitor/` (pacote novo, paralelo a
   `memory/`/`security/`) — nunca importa `tkinter`/`customtkinter`; `ui/desktop/
   dashboard/` (pacote novo, paralelo a `ui/desktop/orb/`) — nunca chama `psutil`/WMI
   diretamente.
6. **Como evitar polling excessivo**: um único coletor central (`SystemMonitorService`),
   nunca um por widget; intervalo configurável (`~1s` métricas, `~2s` processos, padrão
   do pedido); histórico limitado (`deque(maxlen=120)`).
7. **Como manter a GUI responsiva**: toda coleta roda numa `threading.Thread(daemon=True)`
   própria; nenhum `psutil`/WMI é chamado dentro de um callback do Tkinter — a GUI só
   recebe snapshots já prontos, marshalled pelo `BackgroundRunner` existente.
8. **Como integrar ao lifecycle atual**: `main.build_app_services()` (já reportava
   componentes ao `LifecycleManager` desde a V1.3) ganhou mais um: `system_monitor`.
   Encerramento do monitor entra em `SteveApp._shutdown()`, ao lado de
   `runner.close()`/`database.close()` já existentes.
9. **Como evitar coletores duplicados**: `SystemMonitorService.start()` é idempotente
   (`if self.is_running: return`); `SteveApp._open_dashboard()` usa o mesmo padrão de
   guarda de janela única já usado por `_open_settings()`/`SettingsDialog`.

Nada estável foi reescrito sem necessidade: `tools/system.py`, `tools/applications.py`,
`ai/router.py`, `memory/`, `core/context.py` e o núcleo do laço de tool-calling do
Orchestrator não foram tocados — só ganharam publicações de evento opcionais (ver seção 9).

## 4. Nova arquitetura do System Monitor

Uma única fonte de coleta, vários leitores — nenhum widget chama `psutil`/WMI direto:

```
system_monitor/
├── models.py     SystemSnapshot/ProcessSnapshot — dataclasses frozen, só tuplas
├── metrics.py    CPU/RAM/disco (psutil)
├── gpu.py        GpuMonitor — cross-vendor, sem SDK de fabricante (ver seção 6)
├── network.py    RateTracker genérico — rede e E/S de disco reaproveitam a mesma lógica
├── processes.py  ProcessCollector — cpu_percent primado por processo, entre polls
└── service.py    SystemMonitorService — thread própria, publica no EventBus
```

## 5. Estrutura do Dashboard

`ui/desktop/dashboard/window.py::DashboardWindow` (`CTkToplevel`) — 4 abas
(`CTkTabview`): Overview, Performance, Processes, Steve Core. Reaproveita o
`BackgroundRunner` da janela principal (nenhum segundo loop de polling) e o `EventBus`
compartilhado (nenhum segundo sistema de eventos). Aberto pelo botão "📊 Dashboard";
guarda de janela única idêntica à de `SettingsDialog`.

## 6. Métricas implementadas

CPU (uso, por núcleo, frequência, núcleos físicos/lógicos, temperatura best-effort — ver
seção 21), GPU (nome do(s) adaptador(es), utilização, VRAM usada/total, temperatura
sempre indisponível — ver seção 21), RAM (uso%, usada, disponível, total), Disco (uso%,
livre/total, leitura/escrita por segundo), Rede (download/upload por segundo, totais).
**GPU cross-vendor sem SDK de fabricante**: `psutil` não tem suporte a GPU; em vez de
`pynvml`/`GPUtil` (só NVIDIA — a própria máquina de desenvolvimento deste projeto tem uma
AMD Radeon RX 6750 XT dedicada + Intel UHD 770 integrada, **nenhuma NVIDIA**, um teste
real e não hipotético de "não assumir fabricante"), `gpu.py` usa WMI
(`Win32_VideoController`, nomes) + Performance Counters do Windows ("GPU Engine", "GPU
Adapter Memory" — o mesmo mecanismo do Gerenciador de Tarefas desde o Windows 10 1803),
ambos alcançáveis via `pywin32`, **já uma dependência existente** (usada por
`voice/tts.py` para SAPI5) — nenhuma dependência nova foi adicionada. Validado ao vivo
nesta máquina: utilização real (~11-26% observada), VRAM usada real, nomes dos dois
adaptadores corretos. **VRAM total via WMI é conhecida por estourar** (DWORD de 32 bits)
acima de 4GB — confirmado nesta máquina (uma placa de 12GB reporta ~4GB errado via WMI);
`gpu.py` usa em vez disso a chave de registro do driver
(`HardwareInformation.qwMemorySize`), que reportou corretamente ~12GB.

## 7. Monitoramento de processos

`ProcessesTab` (`ttk.Treeview`, estilizado para a paleta ativa) mostra Processo/PID/CPU/
RAM/Status, ordenável por clique no cabeçalho, limitado a 60 linhas exibidas (o
`ProcessCollector` já ordena por CPU desc. e corta em 100 antes disso). **Somente
leitura por construção** — a aba não tem nenhum método capaz de agir sobre um processo,
nenhum botão de ação existe em lugar nenhum do Dashboard. `cpu_percent` é primado por
processo (mesma semântica do `psutil` real: primeira leitura sempre 0.0, valores reais a
partir da segunda) — o mesmo princípio já usado no `GpuMonitor` (V1.4) e implicitamente
em `psutil.cpu_percent()` (V1.0).

## 8. Histórico

`SystemMonitorService` mantém `cpu_history`/`gpu_history`/`ram_history`/
`network_download_history`/`network_upload_history`, todos `collections.deque(maxlen=120)`
(~2 minutos a 1s) — nunca cresce sem limite. `PerformanceTab` só lê esses deques prontos;
`LineGraph` (Canvas puro, sem lib de gráficos) redesenha a partir deles a cada snapshot —
valores `None` (métrica indisponível) geram um gap na linha, nunca são desenhados como 0.

## 9. EventBus utilizado

**Nenhum sistema paralelo foi criado** — tudo no `EventBus` já ativado na V1.3.
`system_monitor/service.py`: `SYSTEM_MONITOR_STARTED`, `SYSTEM_MONITOR_STOPPED`,
`SYSTEM_METRICS_UPDATED`, `PROCESS_LIST_UPDATED`, `NETWORK_METRICS_UPDATED`,
`SYSTEM_MONITOR_ERROR`. `core/orchestrator.py`: `AI_REQUEST_STARTED`,
`AI_RESPONSE_RECEIVED`, `TOOL_STARTED`, `TOOL_COMPLETED` (parâmetro `event_bus`
opcional, `None` por padrão — retrocompatível com todo teste/chamador anterior).
`voice/service.py`: `VOICE_STATE_CHANGED`. `ui/desktop/dashboard/window.py`:
`SYSTEM_DASHBOARD_OPENED`/`SYSTEM_DASHBOARD_CLOSED`. Payloads deliberadamente mínimos
(nome da ferramenta + booleano; nunca conteúdo de mensagem, resultado de ferramenta ou
caminho de arquivo) — Live Activity nunca vê dado sensível porque ele nunca é publicado.

**Callback do EventBus roda na thread que publicou o evento** — para o monitor e para
turnos de conversa/voz, isso quase sempre é uma thread de segundo plano, nunca a
principal do Tk. `DashboardWindow` nunca toca um widget direto num desses callbacks: cada
um só chama `self._runner.post(...)`, reaproveitando o `BackgroundRunner` da janela
principal.

## 10. Live Activity

`ui/desktop/dashboard/live_activity.py::_EVENT_PRESENTATION` mapeia cada evento real
para uma apresentação estilizada (`TOOL_STARTED` → "> CORE MODULE / > EXECUTING",
`TOOL_COMPLETED` → "> OPERATION / > COMPLETE", `STEVE_READY` → "> STARTUP / > READY",
etc.) — a semântica é sempre real, só a apresentação é estilizada. Estado `IDLE` por
padrão; um evento de início muda para um estado ativo, um evento de conclusão
correspondente agenda a volta a `IDLE` após ~2,5s — nunca uma animação contínua
desconectada de eventos reais (testado: eventos não mapeados são ignorados
silenciosamente, sem gerar texto). Sanitização: os eventos publicados por
`core/orchestrator.py` nunca carregam conteúdo sensível em primeiro lugar (payload só
com nome da ferramenta + booleano); `_sanitize()` aplica uma camada defensiva adicional
de redação de caminhos por cima disso.

## 11. Responsividade

Cada aba se religa num grid de 1/2/3 colunas conforme a largura (`<Configure>`), sem
recriar nenhum widget — só `grid_forget()`/`grid()` nos cards/gráficos já existentes.
Validado ao vivo: 300px → 1 coluna, 900px → 3 colunas, sem recriar os frames dos cards
(mesma identidade de objeto antes/depois do resize, confirmado por teste).

## 12. Concorrência/threads

`SystemMonitorService._run()` roda em UMA `threading.Thread(daemon=True)` própria.
`GpuMonitor` mantém sua query PDH de utilização aberta ENTRE chamadas (contador de taxa,
como `psutil.cpu_percent()`, precisa de duas amostras reais para significar algo) em vez
de abrir/amostrar duas vezes por chamada, o que bloquearia ~1s dentro de cada poll — o
intervalo natural entre polls já faz esse papel de "priming". `DashboardWindow` reaproveita
o `BackgroundRunner` já existente da janela principal para toda marshalling GUI — nenhuma
segunda fila/loop de polling foi criada. Fechamento da janela cancela os `after()`
pendentes do Live Activity e remove as assinaturas do `EventBus` — testado que publicar
eventos depois de fechar o Dashboard não levanta exceção.

## 13. Performance

Medido nesta máquina (AMD Ryzen, 16 threads lógicos / 10 físicos, AMD RX 6750 XT + Intel
UHD 770), coletores diretamente, cache do `psutil` já aquecido:

| Coletor | Tempo |
|---|---|
| CPU (uso+freq+núcleos) | ~6 ms |
| Memória | ~3 ms |
| Disco (uso) | ~0,1 ms |
| GPU (utilização+VRAM, contador já primado) | ~40 ms |
| Rede (taxa) | ~5 ms |
| E/S de disco (taxa) | ~0,1 ms |
| Processos (~237 no sistema, top 100 retornados) | **muito variável: ~2 ms a ~900 ms** |

**Achado real, investigado**: a coleta de processos variou de forma significativa entre
execuções idênticas — inicialmente suspeitei do atributo `status` (psutil/Windows), mas
isolando cada atributo (`pid`/`name` sozinhos: sempre ~2-15ms) e repetindo o teste várias
vezes, a variação não correlacionou de forma consistente com quais atributos eram
pedidos — ora uma combinação mais simples era mais lenta que uma mais complexa no mesmo
processo, ora tudo ficava rápido por várias execuções seguidas. Isso aponta para uma
causa externa ao código deste projeto (antivírus/Windows Defender interceptando consultas
de processo, ou contenção de agendamento do SO), não uma ineficiência do coletor. **O que
importa para a conclusão desta etapa**: mesmo no pior caso observado (~900ms), isso fica
folgadamente abaixo do `process_interval` padrão (2s) — o laço em
`SystemMonitorService._run()` já lida com um ciclo mais lento que o intervalo
graciosamente (`max(0, intervalo - decorrido)` nunca fica negativo, o próximo ciclo só
começa imediatamente em vez de acumular atraso) — não há acúmulo, deadlock ou trava.

**Processo do próprio Steve** (medido com o Dashboard aberto e o monitor rodando por
alguns segundos): **~0% de CPU** quando parado (medido num intervalo de 1s),
**~75 MB de RSS**, **24 threads**. Tempo de abertura do Dashboard: sub-segundo
(construção de widgets, sem I/O bloqueante). Intervalo efetivo de atualização:
confirmado ~1s para métricas / ~2s para processos, batendo com a configuração
(`system_monitor_interval_seconds`, padrão 1.0).

## 14. Configuração

Um único campo novo, exatamente como o pedido pedia para evitar configuração artificial:
`Settings.system_monitor_interval_seconds: float = 1.0`, validado (0.1 a 60 segundos,
`SettingsValidationError` fora disso). `dashboard_enabled` **não foi adicionado** — o
Dashboard é aberto por um botão, não precisa de uma flag de liga/desliga separada; nada
na arquitetura atual justificava esse campo. Backward compatible: um `config.json` antigo
sem esse campo carrega normalmente com o default.

## 15. Privacidade

`system_monitor/` nunca importa `requests`/`socket`/`urllib`/`http.client` (verificado
por teste estático) — todas as fontes de dados são locais (`psutil`, WMI, Performance
Counters do Windows). Nenhuma telemetria, nenhum upload de processos/nomes de arquivo/
IPs/métricas/hardware. Os eventos publicados pelo Orchestrator/voz nunca carregam
conteúdo de mensagem, resultado de ferramenta ou caminho de arquivo — a sanitização do
Live Activity é defesa em profundidade sobre payloads que já nascem seguros, não a única
camada de proteção.

## 22. Limitações conhecidas

- **Temperatura de CPU não é confiável em todo hardware** — `MSAcpi_ThermalZoneTemperature`
  (única fonte nativa do Windows) às vezes nem está disponível, e quando está, foi
  observado **congelado em exatos 27,9°C durante 6 segundos de carga sustentada de 8
  threads** nesta máquina — um sensor real se moveria visivelmente. O valor ainda é
  exibido quando presente (é uma chamada de API real, nunca inventada), mas não deve ser
  tratado como preciso em toda máquina — documentado no código e aqui.
- **Temperatura de GPU nunca é reportada** — não existe API do Windows cross-vendor para
  isso, só SDKs por fabricante, fora de escopo por instrução explícita.
- **VRAM total depende de uma chave de registro não documentada oficialmente**
  (`HardwareInformation.qwMemorySize`) — mais precisa que a alternativa oficial (WMI
  `AdapterRAM`, comprovadamente errada acima de 4GB), mas ainda assim não é uma API
  pública garantida entre versões do Windows.
- **Coleta de processos tem tempo altamente variável** (~2ms a ~900ms observados nesta
  máquina) por razões externas ao coletor (provável antivírus/agendamento do SO, não os
  atributos pedidos — ver seção 13) — sempre dentro da margem do intervalo padrão de 2s,
  mas um fator de imprevisibilidade real do ambiente Windows, não deste código.
- **Sem ícone de bandeja no Dashboard** (mesma limitação já documentada na V1.3 para a
  janela principal) — não é um requisito desta etapa.
- **`LineGraph` desenha uma linha contínua mesmo com valores `None` intercalados** (ex.:
  GPU indisponível por um instante) — o ponto ausente é pulado, mas o segmento anterior e
  o seguinte ainda se conectam visualmente em vez de mostrar uma quebra explícita; uma
  imperfeição visual menor, não um dado incorreto (o `None` nunca vira um "0%" desenhado).

## 23. Riscos

- **Nenhum risco de segurança/privacidade novo**: só leitura local (`psutil`/WMI/
  Performance Counters), nenhuma ação destrutiva existe em código algum desta etapa
  (confirmado: nenhuma função de matar/suspender/apagar/bloquear processo, arquivo, IP
  ou serviço foi criada — a aba Processes não tem nenhum método capaz disso).
  `AuditLogger`/redação de segredos já existentes continuam intocados.
- **Achado real corrigido durante o desenvolvimento**: os testes de GUI inicialmente
  usavam um `SystemMonitorService` real com intervalo muito rápido (0,05s) rodando
  simultaneamente a testes que publicavam snapshots sintéticos no mesmo `EventBus` — uma
  corrida genuína entre dado real e dado de teste, que às vezes fazia o widget mostrar o
  dado real em vez do sintético que o teste esperava. Corrigido tornando o fixture
  padrão deliberadamente lento (30s, o suficiente para nunca disparar durante o teste) e
  isolando o ÚNICO teste que precisa do coletor real de verdade rápido, construindo o
  seu próprio.
- **Segundo achado real, também corrigido**: vários testes unitários de
  `start()`/`stop()` do `SystemMonitorService` não mockavam `ProcessCollector.sample()`
  — como `_run()` sempre coleta processos uma vez de verdade no primeiro ciclo (não
  importa o `process_interval`), e essa coleta real mede de ~2ms a ~900ms+ nesta máquina
  (seção 13), o `stop()` desses testes ocasionalmente esperava mais que o previsto sob
  carga concorrente da suíte inteira. Corrigido mockando a coleta de processos em todo
  teste que só verifica start/stop/shutdown — ver seção 20.
- **`GpuMonitor`/`ProcessCollector` mantêm estado (handles/contadores) entre chamadas**
  — por design (necessário para taxas/priming corretos), mas significa que reusar a
  mesma instância entre um `SystemMonitorService` e outro incorretamente poderia
  confundir o priming; `SystemMonitorService` sempre cria as suas próprias instâncias no
  construtor, nunca compartilhadas entre serviços, então esse risco não se materializa
  na prática — registrado para quem for estender isso no futuro.
