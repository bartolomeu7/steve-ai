# V1.4.1 — PATCH 04 — HARDWARE METRICS REPORT

## 1. Auditoria

Antes de qualquer alteração, li integralmente: `system_monitor/metrics.py`,
`system_monitor/gpu.py`, `system_monitor/service.py`, `system_monitor/models.py`,
`system_monitor/network.py`, `system_monitor/processes.py`,
`ui/desktop/dashboard/overview.py`, `ui/desktop/dashboard/performance.py`,
`ui/desktop/dashboard/formatting.py`, `ui/desktop/dashboard/graph.py`,
`settings/config.py`, `tools/system.py` e `tests/test_system_monitor.py`,
`tests/test_dashboard.py`.

Em vez de assumir o comportamento das APIs de hardware, escrevi e executei um script de
diagnóstico real (sem mocks) nesta própria máquina de desenvolvimento (AMD Ryzen 16
lógicos/10 físicos, AMD Radeon RX 6750 XT dedicada + Intel UHD 770 integrada) chamando
diretamente `psutil.cpu_percent()`, `psutil.cpu_freq()`, `psutil.sensors_temperatures()`,
WMI (`Win32_VideoController`), PDH (`GPU Engine`/`GPU Adapter Memory`) e o registro
(`HardwareInformation.qwMemorySize`) nos mesmos padrões que o código de produção usa —
isso revelou 4 problemas reais que a leitura de código sozinha não teria confirmado com
certeza (detalhados na seção 4).

## 2. Métricas analisadas

CPU usage, CPU temperature, CPU frequency, GPU detection, GPU usage, GPU temperature,
VRAM total, VRAM used, RAM, Disk, Network — todas as 11 áreas do escopo desta etapa.

## 3. Fontes utilizadas

| Métrica | Fonte | Já era dependência? |
|---|---|---|
| CPU uso/frequência/núcleos | `psutil.cpu_percent`/`cpu_freq`/`cpu_count` | sim |
| CPU temperatura | nenhuma (ver seção 5) | — |
| GPU nomes | WMI `Win32_VideoController` (`win32com`) | sim (pywin32) |
| GPU uso | Performance Counters "GPU Engine" (`win32pdh`) | sim (pywin32) |
| GPU temperatura | nenhuma (ver seção 9) | — |
| VRAM usada | Performance Counters "GPU Adapter Memory" (`win32pdh`) | sim (pywin32) |
| VRAM total | Registro (`HardwareInformation.qwMemorySize`, `winreg`) | sim (stdlib) |
| RAM | `psutil.virtual_memory()` | sim |
| Disco | `psutil.disk_usage()` | sim |
| Rede | `psutil.net_io_counters()` | sim |

Nenhuma dependência nova foi adicionada. `psutil.sensors_temperatures()` foi avaliado
como possível fonte alternativa de temperatura de CPU e descartado — não existe nesta
plataforma (`AttributeError`, confirmado ao vivo: é Linux/FreeBSD-only no psutil).

## 4. CPU usage

**Problema confirmado e corrigido**: `psutil.cpu_percent(interval=None)` é documentado
pelo próprio psutil como retornando um valor sem sentido na primeira chamada (nada para
comparar ainda). Verificado ao vivo nesta máquina: primeira chamada retornou `0.0`,
segunda (0.3s depois) retornou `26.2` — um valor real e variável. O código anterior não
tratava essa distinção; um `SystemMonitorService` recém-iniciado publicava esse `0.0`
inicial como se fosse uma leitura estável.

**Correção**: nova classe `CpuUsageTracker` (`system_monitor/metrics.py`), uma instância
por `SystemMonitorService` (mesmo padrão de `GpuMonitor`/`RateTracker`), que descarta a
primeira leitura (retorna `None`) e usa as seguintes normalmente. `CpuMetrics.percent`
passou de `float` para `float | None` para poder expressar isso honestamente —
`format_percent()` e o gráfico de histórico (`LineGraph`) já tratavam `None`
corretamente (mesmo padrão já usado para GPU/rede), então nenhuma mudança de UI foi
necessária além disso. Testado com carga real (ver seção 23): valores variam
corretamente entre idle e carga, `per_core_percent` também correto.

## 5. CPU temperature

**Ponto crítico do patch, resolvido por decisão explícita.** `MSAcpi_ThermalZoneTemperature`
(WMI) é a única fonte nativa do Windows — já identificada em V1.4 como potencialmente
não confiável. Esta auditoria **reconfirmou empiricamente, uma segunda vez**: a consulta
retornou exatamente **27.9°C**, o mesmo valor congelado já registrado na V1.4, mesmo após
o tempo decorrido entre as duas versões. `psutil.sensors_temperatures()` foi avaliado
como alternativa e não existe nesta plataforma.

Por regra explícita do patch ("uma fonte já comprovadamente não confiável nunca deve ser
exibida como se fosse real"), `_cpu_temperature_celsius()` foi reescrita: **não consulta
mais WMI**, sempre retorna `None`, com uma docstring detalhada explicando o motivo (duas
confirmações empíricas independentes de valor congelado, ausência de alternativa
cross-vendor sem driver de kernel de terceiros). O Dashboard mostra "Indisponível"
permanentemente para este campo — não é um placeholder temporário, é a decisão final
para esta plataforma sem novas dependências pesadas.

## 6. CPU frequency

Auditado e mantido como estava, com documentação nova. `psutil.cpu_freq()` já expõe
`.current` (o que o código já usava) e `.max` (não usado antes). Achado real desta
auditoria: nesta máquina, `.current` e `.max` retornaram **exatamente o mesmo valor
(3700 MHz) antes, durante e depois de uma carga sustentada de 2 segundos em 100% de um
núcleo** — ou seja, o valor rotulado "atual" comportou-se como a frequência nominal, não
como uma leitura dinâmica real (limitação conhecida de `Win32_Processor.CurrentClockSpeed`
em alguns sistemas AMD).

Diferente da temperatura, esta não é uma limitação universalmente documentada — por
isso não virou N/A. Em vez disso, `CpuMetrics` ganhou um novo campo opcional
`frequency_max_mhz`, e o Dashboard agora mostra ambos lado a lado ("Frequência: 3.70 GHz
(máx: 3.70 GHz)"), permitindo que o usuário note quando os dois números coincidem, sem
esconder a limitação nem inventar uma métrica de "confiança".

## 7. GPU detection

`Win32_VideoController` já listava corretamente os DOIS adaptadores desta máquina (AMD
RX 6750 XT dedicada + Intel UHD 770 integrada) — confirmado ao vivo. O código NUNCA
escolhia um único adaptador; sempre tratou todos os presentes agregadamente para
uso/VRAM (ver seção 8). Isso já era o comportamento antes da PATCH 04, mas não estava
documentado — corrigido apenas a documentação (docstring de classe de `GpuMonitor` +
`docs/ARCHITECTURE.md`), sem implementar seleção de adaptador (explicitamente fora de
escopo: "não implementar suporte complexo a múltiplas GPUs"). Teste novo
(`test_gpu_monitor_multiple_adapters_lists_all_names`) cobre o cenário de 2 adaptadores
explicitamente.

## 8. GPU usage

**Problema confirmado e corrigido — o achado mais concreto desta auditoria.** Verificado
ao vivo: na primeira `CollectQueryData` logo após `AddCounter`, **todos os ~116
contadores "Utilization Percentage" (engine 3D) desta máquina levantaram
`PDH_INVALID_DATA`** (contador de taxa, precisa de 2 amostras). O código anterior tratava
cada falha individual como "pular" e retornava a soma parcial — que, quando TODOS falham,
é `0.0`: indistinguível de uma GPU genuinamente ociosa.

**Correção**: `_utilization_percent()` agora conta quantos contadores tiveram sucesso no
ciclo; se nenhum teve, retorna `None`. Verificado ao vivo: primeira amostra → `None`,
segunda (1s depois) → `47.7`, um valor real. Também corrigido: a soma agregada de
múltiplos adaptadores agora é limitada a 100 (`min(total, 100.0)`) para nunca mostrar mais
que 100% numa métrica que implica escala 0-100, e valores não-finitos (NaN/inf) são
descartados (`math.isfinite`) em vez de propagados.

## 9. GPU temperature

Auditado e mantido — já era `None` sempre (nenhuma API Windows cross-vendor existe sem
SDK de fabricante). Nenhuma mudança necessária; comportamento já correto desde a V1.4.

## 10. VRAM total

Reconfirmado ao vivo: `Win32_VideoController.AdapterRAM` (WMI) retornou `-1048576` para a
AMD RX 6750 XT — um estouro de DWORD 32-bit clássico (interpretado como inteiro
negativo), a mesma limitação documentada já identificada em V1.4. O código já NÃO usa
esse campo — usa a chave de registro `HardwareInformation.qwMemorySize`, que retornou
corretamente **12868124672 bytes (~11.98 GB)**, o valor real da placa. Nenhuma mudança de
lógica necessária aqui — já estava correto.

**Bug real encontrado e corrigido nesta função** (não relacionado à truncagem, um
problema separado): `_memory_bytes()` retornava antes cedo demais quando `win32pdh` não
estava disponível, perdendo o valor de VRAM total mesmo sendo ele obtido via `winreg`
(sem relação com PDH). Corrigido para consultar o registro independentemente da
disponibilidade do PDH.

**Otimização de performance também aplicada aqui** (ver seção 19): o valor agora é
cacheado por instância de `GpuMonitor` (equivalente ao tempo de vida do serviço), já que
é um fato estático de hardware que nunca muda durante a execução.

## 11. VRAM used

Auditado — a fonte (`GPU Adapter Memory`/`Dedicated Usage` via PDH) é um contador do tipo
"gauge" (não precisa de priming, confirmado ao vivo: leitura imediata bem-sucedida sem
erro). Já soma corretamente todos os adaptadores presentes (documentado na seção 17).
Nenhuma mudança de lógica necessária.

## 12. RAM

Auditado — `collect_memory_metrics()` já espelha diretamente `psutil.virtual_memory()`
sem nenhuma aritmética própria; a consistência matemática (usado + disponível ≈ total)
é responsabilidade do próprio psutil, que já é confiável e testado para isso. Nenhum
problema encontrado, nenhuma mudança feita.

## 13. Disk

**Problema confirmado e corrigido**: quando `psutil.disk_usage(path)` falhava (unidade
removível/de rede desconectada), o código retornava um `DiskMetrics` com
`percent=0.0, used_bytes=0, free_bytes=0, total_bytes=0` — que renderizava no Dashboard
como um disco real de 0 bytes, exatamente o tipo de valor fabricado que este patch existe
para eliminar. Corrigido para retornar `None` nos quatro campos (o quinto/sexto,
`read_bytes_per_sec`/`write_bytes_per_sec`, já eram opcionais). `DiskMetrics.percent`/
`used_bytes`/`free_bytes`/`total_bytes` passaram de tipos obrigatórios para `| None`.
Verificado ao vivo: `C:\` real retorna 95.2% de uso real; um caminho inexistente retorna
`None` em todos os quatro campos, sem crash (a exceção real é `FileNotFoundError`, uma
subclasse de `OSError`, já capturada).

O priming de taxas de leitura/escrita (`DiskIoMonitor`, via `RateTracker` compartilhado
com a rede) já retornava `None` corretamente na primeira amostra — nenhuma mudança
necessária, apenas um teste novo dedicado (`test_disk_io_monitor_first_sample_returns_none_rates`)
para cobertura explícita.

## 14. Network

Auditado — já estava correto antes desta etapa: `RateTracker` já retorna `None` na
primeira amostra, já usa `max(0.0, ...)` para nunca produzir uma taxa negativa (protegendo
contra reset/overflow de contador), e usa apenas `psutil.net_io_counters()` (nenhuma
conexão externa é aberta para medir rede). Nenhuma mudança feita.

## 15. Invalid values

- GPU: valores NaN/infinitos agora são detectados (`math.isfinite`) e descartados como
  `None` em vez de propagados (teste `test_gpu_utilization_rejects_non_finite_values`).
- GPU: soma agregada de utilização limitada a 100 (seção 8).
- CPU/GPU temperatura: sempre `None` — a categoria "temperatura absurda" não pode mais
  ocorrer, por construção.
- Disco: falha na consulta agora produz `None`, não um disco fabricado com 0 bytes
  (seção 13).
- RAM/rede: já usavam psutil/contadores diretos sem aritmética própria capaz de
  produzir lixo — nenhum filtro adicional necessário.

## 16. Fallbacks

Nenhum fallback do tipo "fonte não confiável → mostrar algo mesmo assim" foi introduzido
ou mantido. O único "fallback" que existia (CPU temperature: WMI suspeito → mostrar o
número mesmo assim) foi removido — a fonte não confiável agora sempre resulta em `None`,
nunca num número. GPU sem contadores primados, disco inacessível e rede indisponível já
seguiam (e continuam seguindo) o padrão correto: fonte real indisponível → `None`, nunca
um valor de outra fonte menos confiável substituindo silenciosamente.

## 18. Tool consistency

`tools/system.py` (`check_cpu`/`check_ram`/`check_disk`) não expõe temperatura de CPU,
GPU, VRAM ou frequência — apenas uso de CPU/RAM/disco, usando `psutil` diretamente,
igual ao Dashboard. Não existe risco de divergência para os campos endurecidos nesta
etapa (temperatura/frequência/GPU/VRAM), porque a tool simplesmente não os expõe. Para
CPU%/RAM/disco (que ambos expõem), ambos usam a mesma fonte real (`psutil`) com a mesma
semântica — a tool usa uma chamada bloqueante de amostra única (`interval=0.5`,
apropriada para uma chamada isolada de IA), o serviço usa amostragem contínua
(`interval=None`, apropriada para um coletor de longa duração) — abordagens diferentes
do mesmo dado real, não uma divergência de verdade. Nenhuma mudança necessária.

## 19. Performance

Medido ao vivo (script de diagnóstico dedicado, nesta máquina):

- **Cache de nome de adaptador + VRAM total** (nova otimização desta etapa): antes, cada
  ciclo de ~1s repetia uma consulta WMI/COM e uma varredura de registro — medido em
  **~15.25 ms/chamada**. Depois de cacheado (consultado uma vez, reutilizado pelo tempo
  de vida do `GpuMonitor`): **~1.97 ms/chamada** para um `sample()` completo (que ainda
  inclui as consultas PDH de uso/VRAM usada, que precisam ser ao vivo a cada ciclo).
  Economia real de ~13 ms por ciclo de coleta, sem nenhuma nova dependência.
- Nenhuma nova chamada WMI/PDH foi adicionada; a lógica de detecção de falha de priming
  (contagem de sucessos) usa dados já obtidos na mesma `CollectQueryData`, sem custo
  adicional mensurável.
- CPU do processo Steve durante a validação real: 0-9% (variação normal, já registrada
  em etapas anteriores); nenhuma mudança perceptível atribuível a esta etapa.

## 25. Limitações

- A frequência de CPU "atual" pode, nesta e em máquinas semelhantes, refletir a
  frequência nominal em vez de uma leitura dinâmica real — não há como distinguir os
  dois casos programaticamente sem uma fonte melhor (fora de escopo); mostrar `current`
  e `max` lado a lado é a mitigação escolhida, não uma correção do dado subjacente.
- VRAM usada/uso de GPU ainda são agregados (soma) entre todos os adaptadores
  presentes quando há mais de um — documentado, não implementado suporte a seleção de
  adaptador (explicitamente fora de escopo desta etapa).
- Um erro intermitente de Tcl/Tk (`TclError` na criação do interpretador) apareceu em 2
  das 3 execuções completas da suíte, cada vez num teste diferente e não relacionado a
  system_monitor/GPU/CPU — reproduzido zero vezes na terceira execução (400/400 limpos)
  sem nenhuma mudança de código entre as execuções 2 e 3. Classificado como falha
  ambiental intermitente na criação de interpretadores Tcl/Tk sob a carga de ~400 testes
  sequenciais, não uma regressão desta etapa — nenhum código desta etapa toca
  Tkinter/inicialização de GUI.

## 26. Riscos restantes

- Se uma versão futura do driver AMD/Windows passar a reportar `CurrentClockSpeed`
  dinamicamente nesta máquina, o Dashboard mostraria valores diferentes de `max`
  automaticamente — nenhuma ação necessária, o código já lê o valor real a cada ciclo.
- A soma de utilização/VRAM entre adaptadores (seção 25) pode produzir um número
  combinado enganoso se ambas as GPUs estiverem genuinamente ativas ao mesmo tempo —
  mitigado parcialmente pelo clamp a 100%, mas não eliminado; documentado para uma
  eventual PATCH futura se isso se mostrar um problema real em uso.
- A falha intermitente de Tcl/Tk (seção 25) não foi eliminada, apenas caracterizada como
  não-reprodutível de forma determinística — se voltar a ocorrer com frequência em
  validações futuras, merece investigação dedicada (fora do escopo desta etapa de
  hardware metrics).
