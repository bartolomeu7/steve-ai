## 3. Mudanças no banco SQLite

Migração **aditiva e idempotente** sobre a tabela `memories` já existente — nenhuma
linha da V1/V1.1 é tocada ou apagada; roda sem erro tanto num banco novo quanto num já
em uso (`Database._migrate_memories_v1_2()` confere `PRAGMA table_info(memories)` antes
de cada `ALTER TABLE`):

| Coluna | Tipo/Default | Papel |
|---|---|---|
| `category` | `TEXT NOT NULL DEFAULT 'permanent'` | identity/permanent/temporary |
| `key` | `TEXT` | chave estável para upsert/atualização |
| `source` | `TEXT NOT NULL DEFAULT 'user'` | user/explicit_command/inferred/system |
| `confidence` | `REAL NOT NULL DEFAULT 1.0` | confiança na informação |
| `expires_at` | `TEXT` | `NULL` = nunca expira |
| `active` | `INTEGER NOT NULL DEFAULT 1` | soft-delete (0 = esquecida/substituída) |

Mais 3 índices (`idx_memories_category`, `idx_memories_key`, `idx_memories_active`).
`conversation_history` **não mudou** — continua sendo o suporte de SESSION.

## 4. Nova arquitetura de memória

Quatro camadas conceituais, só três vivem na tabela `memories`:

| Camada | Onde vive |
|---|---|
| IDENTITY | texto fixo em `ai/prompts/system_prompt.py::IDENTITY` |
| PERMANENT | `memories`, `category='permanent'`, sem expiração |
| TEMPORARY | `memories`, `category='temporary'`, com `expires_at` |
| SESSION | `SessionManager` (em memória) + `conversation_history` (SQLite) — **não** é uma `category` |

SESSION ficou fora da tabela de propósito: `SessionManager`/`conversation_history` já
cumpriam esse papel desde a V1; colocar "a conversa atual" na mesma tabela que fatos
duradouros misturaria exatamente as camadas que a especificação pediu para separar.

## 5. Como o contexto é construído

`ContextManager.build(session, settings, history_limit=10, user_text=None)` monta, nesta
ordem, o `list[AIMessage]` enviado ao provider:

1. Identidade do sistema (`IDENTITY`)
2. Nome do usuário + nível de proatividade
3. `TOOL_POLICY` (quando usar ferramentas)
4. `MEMORY_POLICY` (quando lembrar/esquecer)
5. Resumo das memórias **relevantes** (não o banco inteiro) — via
   `MemoryService.summarize_for_prompt(query=user_text)`
6. Últimos `history_limit` turnos da sessão atual

Relevância é pontuada por **sobreposição de palavras** (stdlib `re`, sem embeddings/
serviço externo) entre `user_text` (a mensagem atual) e o conteúdo/chave de cada
memória — o que importa agora tem prioridade sobre uma memória antiga e importante mas
fora de assunto. Sem `user_text`, cai para importante-primeiro/mais-recente (comportamento
da V1). O tamanho do prompt fica limitado por um `limit` padrão de 8 memórias e por
truncamento de conteúdo longo em `summarize_for_prompt` — o prompt não cresce sem limite
conforme o banco cresce. `Orchestrator.handle_message()` já passa a mensagem atual do
usuário como `user_text`. O tool-calling nativo (`AIProvider.chat(messages, tools=...)`,
`ToolCall`/`ToolSpec`/`ToolManager`) não foi tocado — `ContextManager` continua devolvendo
só `list[AIMessage]`.

## 6. Regras de memorização

Decididas pelo próprio modelo via `MEMORY_POLICY` (política em texto, não um filtro
determinístico no código — igual ao `TOOL_POLICY` já existente):

- Salvar quando: (a) pedido explícito ("lembre que...", "guarde isso...") ou (b)
  informação claramente duradoura e relevante para o futuro ("meu projeto principal é X").
- Classificar `temporary=true` (expira em 24h) quando a informação vale só para
  agora/hoje ("hoje estou trabalhando na tela de login").
- **Não** salvar: comandos comuns ("abra o Chrome"), perguntas do dia a dia, conversa
  casual sem valor futuro.
- Usar a mesma `key` quando o novo fato corrige/substitui um anterior, em vez de criar
  um fato duplicado/conflitante.
- O campo `content` deve conter a frase completa com o valor específico, nunca só a
  categoria da informação (reforçado depois de um achado real — ver seção 12).

## 7. Regras de atualização/exclusão

- `MemoryService.remember(content, key=..., ...)` é o caminho central de escrita: se já
  existe uma memória **ativa** com a mesma `key`, ela é marcada `active=0` (soft-delete,
  permanece no banco para auditoria) e a nova linha assume como versão ativa — uma
  correção nunca vira uma segunda memória conflitante.
- `forget_by_key(key)` e `forget_matching(search_text)` também fazem soft-delete
  (`active=0`), preservando histórico.
- `delete_memory`/`forget` (API da V1, ainda usada onde já era usada) continuam fazendo
  hard-delete — comportamento antigo intocado.
- `purge_expired()` faz hard-delete apenas de linhas com `expires_at` no passado;
  chamado uma vez na inicialização (`build_app_services`), mas todo caminho de leitura já
  filtra `active=1` e não-expiradas independentemente disso.
- Todas as leituras (`list_memories`, `search_memories`, `get_relevant_memories`,
  `get_active_by_key`) ignoram memórias inativas ou expiradas por padrão.

## 12. Limitações conhecidas

- **Fidelidade do modelo em `content`**: o llama3.2 3B, na primeira tentativa observada
  ao vivo, preencheu `content` só com a categoria da informação ("meu projeto
  principal") sem o valor ("Prime Ges"). Mitigado (não eliminado) fortalecendo a
  descrição do parâmetro `content` na ferramenta e o `MEMORY_POLICY` com um exemplo
  concreto — melhorou nas execuções seguintes, mas por ser um modelo pequeno, variação
  de execução para execução ainda é possível. Não há validação determinística no lado do
  código que rejeite um `content` "curto demais", porque isso rejeitaria fatos
  legitimamente curtos ("Gosta de café.").
- **A `key` de uma memória não é reproduzida em turnos futuros**: `SessionManager`/
  `conversation_history` só guardam o texto final de `user`/`assistant`, nunca os
  argumentos brutos de uma tool call — então o modelo pode não saber a `key` exata usada
  para salvar um fato numa conversa anterior. `ForgetMemoryTool` já cai para
  `search_text` quando `key` não bate (corrigido nesta etapa), mas se o modelo não
  fornecer nenhum `search_text` razoável, o fato pode não ser encontrado.
- **Relevância por sobreposição de palavras é literal**: não entende sinônimos nem
  paráfrase (ex.: "trampo" não vai casar com "trabalho" numa memória salva). Suficiente
  para o escopo desta etapa (sem embeddings/serviço externo, por exigência explícita),
  mas é um limite real de qualidade de recuperação.
- **Sem limite de tamanho total do prompt de sistema**: o número de memórias no resumo é
  limitado (padrão 8) e o conteúdo de cada uma é truncado, mas não há uma checagem
  agregada de caracteres/tokens do prompt final — com memórias individualmente longas
  (até o truncamento de 200 caracteres cada) e histórico de conversa longo, o prompt
  pode crescer mais do que o ideal antes de estourar o limite de contexto do modelo.

## 13. Riscos encontrados (e corrigidos nesta etapa)

- **Bug real em `ForgetMemoryTool.execute()`**: quando o modelo fornecia `key` E
  `search_text` juntos e a `key` não batia com nenhuma memória ativa, o método retornava
  falha imediatamente sem tentar `search_text` — mesmo havendo uma memória que o
  `search_text` teria encontrado. Reproduzido ao vivo (cenário 4 da seção 11, primeira
  tentativa) e corrigido: agora tenta `key` primeiro e cai para `search_text` antes de
  reportar falha. Coberto por um novo teste
  (`test_forget_memory_tool_falls_back_to_search_text_when_key_does_not_match`).
- Nenhum outro risco de segurança/privacidade identificado: `remember_fact`/
  `forget_memory`/`recall_memories` continuam `PermissionLevel.LOW` (mesmo nível das
  outras ferramentas de leitura/escrita local já existentes), passam pelo mesmo
  `PermissionManager`/`AuditLogger`, e nenhum dado sai da máquina.

## 14. Próximo passo recomendado

Nenhum avanço de versão foi feito nesta etapa — aguardando autorização explícita, como
pedido. Quando autorizado, o próximo candidato natural conforme o roadmap já documentado
em `docs/ARCHITECTURE.md` é o **Planner** (`core/planner`, transforma objetivos em planos
de etapas) ou o **wake word** ("Steve...", `voice/wakeword.py` já tem a abstração pronta,
sem implementação) — ambos descritos como pendências futuras, não V1.2. Antes disso, se
fizer sentido, uma pequena iteração isolada sobre a limitação de fidelidade do `content`
observada na seção 12 (ex.: few-shot mais explícito no `MEMORY_POLICY`) poderia melhorar
a qualidade de memorização sem contar como uma nova versão.
